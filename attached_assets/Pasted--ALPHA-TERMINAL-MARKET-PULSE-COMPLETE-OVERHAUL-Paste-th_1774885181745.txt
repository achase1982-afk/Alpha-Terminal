## PART 1: BACKEND – Force Structured JSON Output from the AI

### What to change

Find the backend route/function that calls the LLM (Gemini) for the Market Pulse. Replace the current prompt that asks for a markdown narrative. The new prompt must demand a strict JSON response with absolutely no markdown, no preamble, no backticks, just raw JSON.

### New System Prompt for the Market Pulse LLM Call

```
You are an institutional-grade multi-asset market analysis engine. You do NOT write prose or narratives. You output ONLY a raw JSON object matching the exact schema below. No markdown. No backticks. No preamble. No commentary. Just the JSON object.

Your job is to analyze the provided market data across five signal clusters and produce:
1. A factual data snapshot (what is the market doing)
2. A synthesized cross-asset read with auditable scoring (what does this combination mean)
3. Conditional strategy guidance (what setups does this environment favor)

CRITICAL RULES:
- If any data source is missing, stale (>15 min old), or showing zero volume, you MUST set that cluster's dataQuality to "STALE" or "MISSING" and reduce your confidence accordingly.
- The maxConfidence field equals (number of clusters with "FRESH" dataQuality / 5) * 100. If 4 of 5 clusters have fresh data, maxConfidence = 80. Your confidenceScore can never exceed maxConfidence.
- If confidenceScore < 40, set bias to "NO_EDGE" and actionPlan to a single item: "Insufficient data or conflicting signals. No clear edge. Stand aside."
- "NO_EDGE" is a first-class result, not a fallback. Do not force a directional lean from weak data.
- Each cluster scores from -2 (strongly bearish) to +2 (strongly bullish). The compositeScore is the weighted sum.
- If clusters are in strong disagreement (e.g., rates at +2 and term structure at -2), set hasDivergence to true and populate the divergenceNote explaining the conflict.

WEIGHT MAP:
- rates: 25%
- credit: 20%
- volLevel: 20%
- volTermStructure: 15%
- breadth: 20%

BIAS MAPPING from compositeScore:
- >= +1.0: "STRONGLY_BULLISH"
- +0.3 to +0.99: "BULLISH"
- -0.29 to +0.29: "NEUTRAL"
- -0.99 to -0.3: "BEARISH"
- <= -1.0: "STRONGLY_BEARISH"
- (override to "NO_EDGE" if confidenceScore < 40)

ACTION PLAN RULES:
1. The 30 macro indicators (VIX, VVIX, VIX9D, VIX3M, TNX, TYX, HYG, LQD, IEF, ADVN, DECN, TICK, TRIN, ADD, NYICDX, SKEW, etc.) are DATA INPUTS ONLY. NEVER suggest trading these instruments directly. They measure the market environment -- they are not trade targets.

2. The Action Plan translates the macro environment into STRATEGY GUIDANCE:
   - What TYPE of strategy is favored by this environment (premium selling, directional, hedging, no-trade)
   - What DIRECTION is supported (bullish, bearish, neutral)
   - What RISK POSTURE is appropriate (full size, reduced, quarter size, stand aside)
   - What CONDITIONS would confirm or invalidate an entry

3. If the user has configured preferred tickers in their Strategy Settings, reference those tickers in the action plan. If no preferred tickers are configured, use broad market references (SPY, QQQ) or say "apply to your preferred tickers."

4. If the user has configured allowed strategies in their Strategy Settings, only suggest strategies from their allowed list. If no preferences are set, suggest whatever strategy the environment warrants.

5. NEVER include specific entry prices, stop losses, or price targets for individual stocks in the Market Pulse. The Market Pulse is a MACRO environment tool. Specific trade entries with price levels belong in the Options Strategist or Technical Analysis features, not here.

6. Examples of GOOD action plan items:
   - "IF VIX compressing below 30 with bullish breadth, THEN environment favors selling premium via put credit spreads on SPY/QQQ"
   - "IF rates falling + credit confirming + breadth positive, THEN aggressive long positioning warranted via bull call spreads on preferred tickers"
   - "IF VIX term structure inverted with SKEW elevated, THEN reduce position sizing and favor defined-risk strategies only"
   - "IF breadth data stale and VIX above 30, THEN no clear edge. Reduce exposure or stand aside until confirmation."

7. Examples of BAD action plan items (NEVER do this):
   - "Long HYG at 79.015 with stop at 78.85" -- HYG is a macro indicator, not a trade target
   - "Short VIX at 29.95 with target 29.33" -- VIX is a macro indicator
   - "Buy LQD at 108.45" -- LQD is a macro indicator
   - "Buy SPY at 636.50 with stop at 635.00" -- specific price entries belong in Options Strategist / Technical Analysis, not Market Pulse
```

## PART 9: LIVE AI THINKING STREAM (Market Pulse + Options Strategist)

### Overview

Gemini 2.5 Pro emits “thinking” tokens before its final response. These thinking tokens contain the AI’s actual reasoning process – what data it’s examining, what connections it’s drawing, what conflicts it’s noticing. Instead of showing fake loading messages, we stream these thinking tokens to the frontend in real time so the user can watch the AI reason through the market data live.

This applies to TWO features:

1. **Market Pulse** (PULSE sub-tab) – when generating or refreshing the pulse
1. **Options Strategist** (STRATEGIST sub-tab) – when generating a strategy analysis

### Backend Streaming Architecture

#### Switch from request/response to streaming

For both the Market Pulse and Options Strategist LLM calls, switch from a standard `await generateObject()` or `await generateText()` call to a **streaming** call. The AI SDK supports this via `streamText()` or `streamObject()`.

Gemini 2.5 Pro with thinking enabled emits two types of content:

- **Thinking tokens:** The model’s internal reasoning (emitted first, streamed incrementally)
- **Final response:** The actual JSON output (emitted after thinking is complete)

#### Server-Sent Events (SSE) endpoint

Create a streaming endpoint (or modify the existing ones) that uses Server-Sent Events to push data to the frontend in real time. The flow:

```
1. Frontend sends POST to /api/market-pulse/stream (or similar)
2. Backend initiates streaming Gemini call with thinking enabled
3. As thinking tokens arrive, backend forwards them to frontend via SSE:
   event: thinking
   data: {"text": "Examining VIX at 29.86, down 3.19% on the session..."}

4. When thinking completes and the final JSON response arrives:
   event: result  
   data: {"type": "complete", "pulse": { ...the full Market Pulse JSON... }}

5. If an error occurs:
   event: error
   data: {"message": "Generation failed. Please try again."}

6. Stream closes.
```

#### Implementation with AI SDK (Vercel AI SDK pattern)

```typescript
// Backend route handler (Express)
import { streamText } from 'ai';
import { google } from '@ai-sdk/google';

app.post('/api/market-pulse/stream', async (req, res) => {
  // Set SSE headers
  res.setHeader('Content-Type', 'text/event-stream');
  res.setHeader('Cache-Control', 'no-cache');
  res.setHeader('Connection', 'keep-alive');

  try {
    const result = streamText({
      model: google('gemini-2.5-pro', {
        // Enable thinking -- the AI SDK / Gemini API config for this
        // may use a parameter like `thinkingConfig` or similar.
        // Check the current AI SDK docs for the exact parameter name.
      }),
      system: MARKET_PULSE_SYSTEM_PROMPT,
      messages: [{ role: 'user', content: buildUserMessage(req.body) }],
    });

    // Stream thinking tokens as they arrive
    for await (const part of result.fullStream) {
      if (part.type === 'reasoning') {
        // These are the thinking tokens
        res.write(`event: thinking\ndata: ${JSON.stringify({ text: part.text })}\n\n`);
      } else if (part.type === 'text-delta') {
        // This is the final response being built
        // We can optionally stream this too, or wait for completion
      }
    }

    // Get the final complete text response
    const finalText = await result.text;
    const parsedPulse = JSON.parse(finalText);
    // Validate with Zod schema here

    res.write(`event: result\ndata: ${JSON.stringify({ type: 'complete', pulse: parsedPulse })}\n\n`);
    res.end();

  } catch (error) {
    res.write(`event: error\ndata: ${JSON.stringify({ message: 'Generation failed. Please try again.' })}\n\n`);
    res.end();
  }
});
```

**IMPORTANT:** The exact API for accessing thinking/reasoning tokens depends on the current version of the AI SDK and the Gemini API. The pattern above is illustrative. Check the AI SDK documentation for:

- How to enable thinking mode for Gemini 2.5 Pro (it may be a model config option, a parameter like `thinkingConfig: { thinkingBudget: 8000 }`, or enabled by default)
- How thinking tokens surface in the stream (they may come as `reasoning` parts, `thought` parts, or similar)
- If using `@ai-sdk/google`, check if there’s a specific way to enable and capture thinking output

The key requirement: thinking tokens must be captured and forwarded to the frontend as they arrive. The final JSON response must be captured separately, parsed, validated, and sent as a distinct event.

### SSE vs WebSocket Decision

Use SSE (Server-Sent Events) for this, NOT the existing WebSocket connection. Reasons:

- SSE is simpler for one-directional server-to-client streaming
- Each generation is a discrete request with a beginning and end
- The existing WebSocket is for Schwab market data streaming – keep concerns separated
- SSE works natively with fetch() and EventSource in the browser
- If the existing WebSocket architecture makes SSE difficult, it’s acceptable to multiplex thinking events over the existing WebSocket, but SSE is preferred for simplicity

- **Background:** Dark, near-black (zinc-950 or existing terminal bg)
