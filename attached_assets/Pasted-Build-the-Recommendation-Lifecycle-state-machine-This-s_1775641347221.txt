Build the Recommendation Lifecycle state machine. This system tracks every trade recommendation from the moment it is created through order placement, execution, monitoring, and close. It is the central state management layer that all other systems reference to know the current status of any recommendation or position. Create a server-side state store using Drizzle ORM with a recommendations table. Each recommendation record contains: id as a unique identifier, ticker symbol, strategyType from the Strategist output, direction BULLISH or BEARISH or NEUTRAL, mode which trading mode generated it (1 through 4), state which is the current lifecycle state, legs as a JSON object containing the contract symbols and strikes and expiration for each leg, entryPrice as the credit received or debit paid, maxLoss in dollars, maxGain in dollars, contracts count, scannerScore if it came from the scanner or null, pulseComposite and pulseConfidence at the time of recommendation, eventConflicts from the calendar guard, createdAt timestamp, updatedAt timestamp, stateHistory as a JSON array of all state transitions with timestamp and fromState and toState and reason, exitPrice if closed, realizedPnL if closed, closedAt if closed, and source which is APP for trades placed through Alpha Terminal or EXTERNAL for trades detected from Schwab that were placed through TOS. The lifecycle states are: SCANNING which means the scanner is evaluating, RECOMMENDED which means the Strategist has output criteria, PRICED which means the Risk Gate has fetched live pricing, CONFIRMED which means the user tapped Place Order and revalidation passed, WORKING_ENTRY which means the order has been submitted to Schwab and is working, PARTIALLY_FILLED which means some contracts filled but not all, EXECUTED which means the entry order is fully filled and the position is open, MONITORING which means exit alerts are active on this position, EXIT_STAGED which means a GTC profit target or other exit order has been placed, EXIT_WORKING which means an exit order is working at Schwab, CLOSED which means the position is fully closed with P&L recorded, CANCELLED which means the user or system cancelled before execution, EXPIRED which means the entry order expired without filling, and REJECTED which means Schwab rejected the order. State transitions must be unidirectional for terminal states. CLOSED, CANCELLED, EXPIRED, and REJECTED are terminal. Once a recommendation reaches a terminal state, no event from any source can change it. Implement this as a state rank check. Assign each state a numeric rank: SCANNING is 1, RECOMMENDED is 2, PRICED is 3, CONFIRMED is 4, WORKING_ENTRY is 5, PARTIALLY_FILLED is 6, EXECUTED is 7, MONITORING is 8, EXIT_STAGED is 9, EXIT_WORKING is 10, CLOSED is 100, CANCELLED is 101, EXPIRED is 102, REJECTED is 103. Before any state transition, check that the new state rank is higher than the current state rank. If not, log a warning and reject the transition. The only exception is CONFIRMED reverting to PRICED if the revalidation timeout expires, which is a defined backward transition. Every state transition must update the updatedAt timestamp and append to the stateHistory array with the timestamp, previous state, new state, and reason for the transition. CONFIRMED state has a timeout. If the order is not submitted within 90 seconds of confirmation, prompt the user. If not submitted within 3 minutes, auto-revert to PRICED and log the reason as “confirmation timeout.” Now build the order state integration. When an order is placed through the Risk Gate, create or update the recommendation record with the Schwab order ID. When ACCT_ACTIVITY WebSocket events arrive, map them to state transitions: OrderCreated maps to WORKING_ENTRY. ExecutionCreated maps to either PARTIALLY_FILLED or EXECUTED depending on whether the fill quantity equals the total order quantity. CancelAccepted maps to CANCELLED. OrderRejected maps to REJECTED. OrderExpired maps to EXPIRED. Before processing any WebSocket event, look up the recommendation by Schwab order ID and check the state rank. If the recommendation is already at a terminal state, skip the event and log it as a duplicate or late arrival. This is the downgrade guard that prevents the backup poller from regressing state. Now build deduplication. Create an in-memory seen-set as a Map keyed by a composite of Schwab order ID plus event type. Before processing any order event from either the WebSocket handler or the portfolio route broadcast, check the seen-set. If the key exists, skip processing. If it does not exist, add it with a timestamp and process normally. Use a 60-second TTL on entries. Run a cleanup every 30 seconds that removes entries older than 60 seconds. Export the seen-set add function so that the portfolio.ts route handlers can register their immediate broadcasts in the same set. Now build reconnect reconciliation. When the Schwab WebSocket reconnects after a disconnect, indicated by a successful LOGIN followed by ACCT_ACTIVITY SUBSCRIBED, immediately call the Schwab orders API to fetch all orders updated in the last 10 minutes. For each order returned, look up the corresponding recommendation by Schwab order ID. Compare the order status from the API against the current recommendation state. If the API shows a more advanced state, transition the recommendation and broadcast the appropriate alert. This catches any events that were missed during the disconnect. Do not wait for the next 30-second polling cycle. Now build degraded monitoring detection. Track the timestamp of the last successful ACCT_ACTIVITY event or SUBSCRIBED confirmation. If more than 2 minutes pass with no events and the WebSocket connection state shows disconnected, set a degradedMonitoring flag to true. Send a single push notification: “Real-time order monitoring is degraded. WebSocket disconnected for over 2 minutes. Check positions in TOS.” On the frontend, if degradedMonitoring is true, show a red banner below the header: “Order monitoring degraded. Connection lost.” When the WebSocket reconnects and reconciliation completes, clear the flag, remove the banner, and send a push: “Real-time monitoring restored.” Now build external trade detection. When the 30-second backup poller finds a position that has no matching recommendation record in the state store, it was placed through TOS or another platform. Create a new recommendation record with source set to EXTERNAL, state set to EXECUTED, and populate what fields are available from the Schwab positions API. Flag it in the frontend with a different visual treatment so the user knows Alpha Terminal is tracking it but did not originate it. For the frontend, add a Recommendations view accessible from the Portfolio tab that shows all active and recent recommendations with their current state. Each card shows the ticker, strategy, current state with a colored badge, entry price, current P&L if executed, time in trade, and the state history as an expandable timeline. Terminal state cards (CLOSED, CANCELLED, EXPIRED, REJECTED) should be visually dimmed and sorted below active ones. Show realized P&L on closed cards in green or red. For partially filled orders, show the filled quantity versus total and the average fill price. For the API layer, create these endpoints: GET /api/recommendations returns all active recommendations. GET /api/recommendations/:id returns a single recommendation with full state history. PATCH /api/recommendations/:id/state for manual state transitions if needed for edge cases. GET /api/recommendations/stats returns summary stats like total trades, win rate, average P&L, for the performance tracking foundation. All recommendation state transitions should be logged at info level with the recommendation ID, previous state, new state, and reason. Any rejected transitions meaning a downgrade attempt should be logged at warn level. Do not build exit order staging yet. Do not build automatic exit placement. Do not build P&L calculation for open positions beyond what Schwab provides. Do not modify the Market Pulse scoring engine. Do not modify the scanner or strategist logic. This is purely the state management and lifecycle layer that sits between the Risk Gate and the exit order system that comes next. That is all.​​​​​​​​​​​​​​​​
