Build a Failure Telemetry system that logs errors, failures, and anomalies across all Alpha Terminal server-side systems so problems are visible instead of silent. This is not a user-facing feature. It is an internal diagnostic layer that helps you debug issues without digging through raw server logs. Create a Drizzle ORM table called failure_log with these fields: unique id, timestamp, system which identifies where the failure occurred as one of SCHWAB_API, SCHWAB_STREAM, IBKR, YAHOO, SEC_EDGAR, SCANNER, STRATEGIST, RISK_GATE, EXIT_STAGING, PUSH_NOTIFICATION, or MARKET_PULSE, severity which is one of INFO, WARN, ERROR, or CRITICAL, message as a short human-readable description, details as a JSON object containing whatever context is relevant like request parameters or response codes or stack traces, resolved as a boolean defaulting to false, and resolvedAt timestamp. Instrument the following failure points across the existing codebase. For Schwab API calls: log every non-200 response with the endpoint, status code, and response body. Log every timeout. Log every OAuth token refresh failure. Log rate limit responses (429) with the retry-after header value. For Schwab WebSocket: log every disconnect with the duration of the previous session. Log every failed reconnect attempt. Log every LOGIN failure. Log when ACCT_ACTIVITY subscription fails or is not confirmed within 10 seconds of sending. Log when the seen-set dedup blocks an event so you can verify it is working correctly at INFO level. For IBKR Gateway: log every connection failure. Log when breadth or PCR data stops arriving for more than 60 seconds during market hours. For Yahoo Finance: log every failed earnings calendar fetch. Log when the response format changes or parsing fails. For SEC Edgar: log every failed insider transaction fetch. For the Scanner: log when a scan completes with zero results after filtering, including how many tickers failed each filter stage and why. Log when any Schwab API call within the scan pipeline fails. For the Strategist: log when the event calendar guard blocks a trade, including which event caused the block. Log when no trading mode qualifies. For the Risk Gate: log when options chain fetch fails. Log when no strikes match the delta targets. Log when liquidity is below threshold. Log when the pre-submit revalidation detects a price move exceeding 15 percent. Log when the portfolio exposure cap blocks a trade. For Exit Order Staging: log every orphaned exit order that gets cancelled with the reason. Log every rejected or expired exit order. Log every stop alert that fires. Log every time stop alert that fires. Log when a staged exit fill is detected. For Push Notifications: log every failed push delivery with the subscription endpoint and error. Log when a push subscription is removed due to a 410 Gone response. For Market Pulse: log when the Claude narrative API call fails or times out. Log when confidence drops below 20 which suggests severe data issues. Log when the regime shock detector transitions between states. For every log entry, use the existing Pino logger at the appropriate level (info, warn, error) AND write to the failure_log database table. This gives you both real-time log output and a queryable history. Create a single API endpoint GET /api/telemetry that returns failure log entries. Accept query parameters for system to filter by system, severity to filter by severity, since as an ISO timestamp to get entries after a date, and limit defaulting to 100. Sort by timestamp descending so newest failures show first. Create a simple Telemetry page accessible from the Settings sidebar. It does not need to be fancy. Show a table of recent failures with timestamp, system, severity, and message. Color code by severity: gray for INFO, yellow for WARN, red for ERROR, flashing red for CRITICAL. Add filter buttons at the top to filter by system and severity. Add a count badge on the Settings sidebar item that shows the number of unresolved ERROR and CRITICAL entries so you know at a glance if something is broken. Add a button on each row to mark it as resolved. Add a “Clear Resolved” button to remove old resolved entries from the view. Implement automatic cleanup. Delete failure_log entries older than 30 days to prevent the table from growing unbounded. Run the cleanup once daily. For CRITICAL severity entries specifically, send a push notification to the user immediately. CRITICAL should only be used for: Schwab OAuth token refresh failure which means all API calls will fail, Schwab WebSocket disconnected for more than 5 minutes during market hours, and IBKR Gateway down during market hours when breadth data feeds the scoring engine. Everything else is ERROR or below. Do not add telemetry to the frontend WebSocket message handler. Do not add client-side error tracking. Do not add performance metrics or timing data. Do not modify any existing system behavior. This is purely adding log statements and database writes at failure points in existing code. Keep it lightweight. That is all.​​​​​​​​​​​​​​​​
